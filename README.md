## Три способи запуску

### 1. Через __main__.py

```
python -m pyside_example
```

### 2. Напряму (для IDE run config)

```
python pyside_example/app.py
```

### 3. app.py

Легко імпортувати з тестів або зовнішнього launcher-скрипта
без побічних ефектів — бо логіка в `run()`, а не на рівні модуля.

# Архітектура PySide6 з UI-файлом

## Концептуальний розподіл відповідальностей

```
UI-файл (.ui)
    ↓ завантажує
BaseWindow           — "обгортка" над UI-файлом, чистий доступ до віджетів
    ↓ наслідує
MainWindow           — View: прив'язка сигналів, оновлення UI, жодної логіки
    ↓ використовує
MainWindowController — Logic: бізнес-логіка, стан, обробка подій
```

## Де шукати і зберігати віджети

**Метод пошуку** — у `BaseWindow`, бо це його єдина відповідальність:
завантажити UI й надати типізований доступ до віджетів.

**Об'єкти віджетів зберігаються у** `MainWindow` (або теж у `BaseWindow`,
якщо потрібна повну ізоляцію від Qt-типів у контролері).

## Де розміщувати обробники сигналів

Обробники (`_on_submit`, `_on_close` тощо) — у `MainWindow`, бо вони:

- читають стан UI-віджетів (`self.input_field.text()`)
- викликають контролер
- оновлюють UI результатом

Контролер **не знає про існування кнопок і лейблів** — він отримує чисті дані й повертає чисті дані.
Це робить його тестованим без Qt.

## Структура пакетів

Стандартна конвенція: my-project → my_project

```
pyside-example/                     ← назва репозиторію/теки (kebab-case)
└── pyside_example/                 ← кореневий пакет (snake_case, PEP 8)
|    ├── __init__.py
|    ├── __main__.py                 ← тонкий: лише import + виклик                 
|    ├── app.py                      ← QApplication, ініціалізація, запуск
|    │
|    ├── ui/
|    │   ├── __init__.py
|    │   ├── base_window.py          # завантаження UI, _find_widget
|    │   └── main_window.py          # View: віджети, сигнали, делегування
|    │
|    ├── controllers/
|    │   ├── __init__.py
|    │   └── main_window_controller.py
|    │
|    └── resources/
|        └── main_window.ui
└── tests/
```

## Резюме принципів

| Питання                        | Відповідь                              |
|--------------------------------|----------------------------------------|
| Метод `_find_widget`           | `BaseWindow`                           |
| Зберігання об'єктів віджетів   | `MainWindow` (поля класу)              |
| Прив'язка сигналів (`connect`) | `MainWindow._connect_signals()`        |
| Обробники сигналів (`_on_*`)   | `MainWindow`, але делегують контролеру |
| Бізнес-логіка                  | `MainWindowController`                 |
| Контролер знає про Qt?         | Ні — тільки чисті типи                 |

## `sys.exit(app.exec())` vs `app.exec_()`

### `sys.exit(app.exec())` — що це і навіщо

`app.exec()` — головний цикл подій

Це **Qt event loop** — блокуючий виклик, який:

- чекає на події (кліки, введення, таймери, сигнали)
- диспетчеризує їх до відповідних обробників
- **повертає код завершення** (0 = успіх, інше = помилка) коли останнє вікно закрито
  або викликано `QApplication.quit()`

### `sys.exit(...)` — навіщо огортати

Передає код завершення Qt **операційній системі**. Це важливо для:

- CI/CD пайплайнів (перевірка чи програма завершилась коректно)
- запуску через shell-скрипти (`if ./app; then ...`)
- будь-якого зовнішнього процесу що чекає на exit code

Без `sys.exit()` Python завжди поверне 0 незалежно від того як завершився Qt.

### `app.exec_()` — застарілий синонім

`exec_()` існував у **PyQt4/PyQt5/PySide2**, тому що `exec` було зарезервованим словом у Python 2:

```
# Python 2 — exec це statement, тому Qt додав підкреслення
app.exec_()
```

У Python 3 exec став звичайною функцією, тому:

```
# PySide6 / PyQt6 — правильно
app.exec()

# PySide6 — exec_() ще існує як alias, але deprecated
app.exec_()  # працює, але не варто використовувати
```

**Висновок:** у PySide6 завжди потрібно використовувати `sys.exit(app.exec())`.

# `:/ `— це Qt Resource System

Двокрапка означає що шлях вказує **не на файлову систему**,
а на **вбудований ресурс** скомпільований у Qt resource system.

## Як це працює

```
:/ui/main_window.ui               ← віртуальний шлях у Qt resource tree
/home/user/app/ui/main_window.ui  ← реальний шлях на диску
```

Qt має власну віртуальну файлову систему.
Ресурси компілюються у бінарний `.rcc` файл
або вбудовуються прямо в executable — і потім читаються через `:/`.

У PySide6 це робиться через `.qrc` файл

```
<!-- resources.qrc -->
<RCC>
    <qresource prefix="/ui">
        <file>forms/main_window.ui</file>
    </qresource>
</RCC>
```

Потім компілюється:

```
pyside6-rcc resources.qrc -o pyside_example/resources_rc.py
```

І імпортується у `app.py`:

```
import pyside_example.resources_rc  # після цього :/ шляхи працюють
```

## Для чого `__all__`

`__all__` — явно визначає що експортується при `from package import *`.

```
# без __all__
from pyside_example.ui.dispatching import *  # імпортує ВСЕ, включно з logging, threading і т.д.

# з __all__
__all__ = ["ClickDispatcher", "acquiring"]
from pyside_example.ui.dispatching import *  # імпортує тільки ці два
```

Але `import *` — погана практика сама по собі, тому `__all__` для цього майже не потрібен.

Реальна користь `__all__` — документація і підказки в IDE: дивлячись на `__init__.py` одразу видно що є публічним, а що внутрішнє. 
Але це конвенція, не захист — нічого не заважає імпортувати напряму з файлу.

Для простого проєкту `__all__` — зайве. Достатньо просто реекспортувати в `__init__.py`.
